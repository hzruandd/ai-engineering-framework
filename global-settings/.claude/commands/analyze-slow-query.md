### 步骤1：调用分析脚本

1. **确认Excel文件路径**
   - 用户会提供慢查询Excel文件路径

2. **执行Python脚本**
   ```bash
   python .claude/analyze_slow_queries.py <excel_file_path> --output doc/慢查询分析报告_<日期>.md
   ```

   **注意**：
   - 使用相对路径调用脚本
   - 输出报告到doc目录，使用当前日期命名
   - 如果遇到编码错误（Windows GBK问题），忽略即可，报告已正常生成

### 步骤2：读取分析报告

阅读Python脚本生成的报告文件，重点关注：

1. **总体统计**
   - 总慢查询次数
   - 平均查询时间
   - 最大/最小查询时间

2. **TOP 10最慢的SQL**
   - 耗时最长的SQL语句
   - 执行时间分布

3. **慢查询类型分析**
   - 按频率排序的TOP 5慢查询模式
   - 每种类型的出现次数、平均耗时、涉及的表

4. **涉及的表清单**
   - 高频访问的表（按出现次数排序）

5. **使用的函数清单**
   - 哪些函数被频繁使用
   - 重点关注：HOUR()、DATE_SUB()、DATE_FORMAT()等动态函数

6. **WHERE/GROUP BY/ORDER BY字段**
   - 查询条件中的字段
   - 分组和排序字段
   - 这些字段是否有索引

### 步骤3：深度根因分析

基于报告内容，进行深度分析，找出以下问题的根本原因：

#### 3.1 SQL层面根因分析

**必须分析的维度**：

1. **动态函数导致索引失效**
   - 检查是否使用了HOUR()、DATE_SUB()、DATE_FORMAT()等函数
   - 分析：这些函数为什么导致慢查询？
   - 根因：动态函数在WHERE条件中会导致索引失效，每行都需要计算

2. **SELECT * 问题**
   - 检查是否有大量SELECT *查询
   - 分析：宽表查询为什么慢？
   - 根因：传输大量无用字段，增加网络IO和内存开销

3. **24个UNION ALL问题**
   - 检查是否有大量UNION ALL拼接
   - 分析：为什么使用UNION ALL而不是GROUP BY？
   - 根因：可能是为了补全24小时数据，但导致SQL执行24次扫描

4. **前导模糊查询**
   - 检查是否有LIKE '%xxx%'或LIKE '%xxx'
   - 分析：为什么前导模糊查询慢？
   - 根因：无法使用索引，需要全表扫描

5. **大量IN条件**
   - 检查IN子句是否包含500+个值
   - 分析：为什么大量IN条件慢？
   - 根因：SQL解析开销大，可能导致优化器选择错误的执行计划

6. **缺少索引**
   - 对比WHERE/GROUP BY/ORDER BY字段与数据库索引
   - 找出哪些高频字段没有索引

#### 3.2 数据库层面根因分析

**必须分析的维度**：

1. **表结构问题**
   - 表是否有合理的主键和索引
   - 表是否按日期分区
   - 字段类型是否合适（如VARCHAR(500)可能过大）

2. **索引策略问题**
   - 是否使用了Doris的INVERTED索引（适用于低基数字段）
   - 是否使用了BITMAP索引（适用于超低基数字段）
   - 是否有冗余索引或无用索引

3. **数据模型问题**
   - 表使用的是UNIQUE KEY还是AGGREGATE KEY
   - 数据模型是否适合当前查询模式

4. **分区问题**
   - 是否按日期分区
   - 查询是否能利用分区裁剪

#### 3.3 应用层面根因分析

**必须分析的维度**：

1. **查询频率问题**
   - 哪些查询被频繁调用（> 100次/天）
   - 是否有N+1查询问题

2. **缓存策略问题**
   - 高频查询是否使用了Redis缓存
   - 缓存命中率如何

3. **业务逻辑问题**
   - 是否有不必要的复杂查询
   - 是否可以通过预聚合表优化

### 四、优化方案

#### 4.1 短期优化方案（1-2周）

##### 优化1：预计算小时字段（优先级：P0）

**方案描述**：
- 在表中添加in_hour和out_hour字段（TINYINT类型）
- 通过Flink SQL实时计算并填充
- SQL改用预计算字段，不再使用HOUR()函数

**实施步骤**：

**Step 1：修改Doris表结构**
```sql
-- 生产环境
ALTER TABLE parking_parking_list
ADD COLUMN in_hour TINYINT COMMENT '入场小时(0-23)',
ADD COLUMN out_hour TINYINT COMMENT '出场小时(0-23)';

-- 添加INVERTED索引
ALTER TABLE parking_parking_list
ADD INDEX idx_in_hour (in_hour) USING INVERTED,
ADD INDEX idx_out_hour (out_hour) USING INVERTED;
```

**Step 2：修改Flink SQL任务**
```sql
INSERT INTO doris_parking_parking_list
SELECT
    ...,
    create_time,
    HOUR(create_time) AS in_hour,    -- 新增
    out_time,
    HOUR(out_time) AS out_hour,      -- 新增
    ...
FROM mysql_cdc_parking_parking_list;
```

**Step 3：修改Java代码**

文件：`city-parking-statistics-api/src/main/java/cn/city/parking/statistics/api/entity/ParkingList.java`

```java
@Schema(description = "入场小时(0-23)")
private Integer inHour;

@Schema(description = "出场小时(0-23)")
private Integer outHour;
```

文件：`city-parking-statistics-server/src/main/resources/mapper/parking/ParkingListMapper.xml`

优化前：
```xml
WHERE HOUR(out_time) = #{hour}
GROUP BY HOUR(out_time)
```

优化后：
```xml
WHERE out_hour = #{hour}
GROUP BY out_hour
```

**预期效果**：
- 查询时间：15秒 → 2秒（↓87%）
- 数据库CPU：峰值60% → 20%
- 索引扫描代替全表扫描

**风险评估**：
- 风险等级：中
- 影响范围：需要修改Flink任务、数据库表、应用代码
- 回滚方案：SQL使用CASE WHEN fallback逻辑，兼容NULL值

**部署计划**：
- Week 1：Doris添加字段 + INVERTED索引
- Week 2：修改Flink SQL，启动实时计算
- Week 3：部署优化代码，监控效果

**如果优化后性能不如预期**：
1. 立即回滚代码到优化前版本
2. SQL使用CASE WHEN fallback逻辑，兼容NULL值
3. 保留hour字段和索引，不删除（无副作用）

**回滚SQL**：
```sql
-- 使用fallback逻辑，兼容NULL值
WHERE CASE
    WHEN out_hour IS NOT NULL THEN out_hour
    ELSE HOUR(out_time)
END = #{hour}
```
