## 1. 数据库设计原则（业务场景驱动，最高原则）

> 本规范最重要的方法论。所有数据库设计、SQL 生成、代码生成、Review 检查都以此为出发点。

### 1.1 设计必须由业务场景驱动

**禁止先建表、后补索引。** 正确的设计顺序是：

```
业务场景
   ↓
访问模式（谁、在什么条件下、以什么频率读写）
   ↓
SQL（具体的 WHERE / JOIN / ORDER BY / GROUP BY / 分页）
   ↓
索引（支撑上述 SQL 的最优索引）
   ↓
表结构（字段类型、主键、约束）
```

含义：

- 先想清楚"这张表将被怎样查询和写入"，再决定字段与索引。
- 每一个索引都必须能回答："它支撑哪一条 SQL？"没有查询场景的索引不允许存在。
- 每一个字段类型都必须能回答："它的取值范围与业务语义是什么？"

### 1.2 设计输出必须自解释

数据库设计产出（DDL + 索引 + 查询 SQL）必须附带：主键方案与理由、每个索引支撑的查询与列顺序理由、关键查询的访问路径与预期数据量、已识别的性能风险。

## 2. 字段设计规范

### 2.1 类型规范

| 业务场景 | 推荐类型 | 说明 |
|---|---|---|
| ID / 主键 | `bigint`（新表）或 `varchar(64)`（存量/外部ID） | 见第 3 章主键规范 |
| 状态 / 枚举 / 布尔 | `tinyint` | 禁止用 `varchar` 存状态；0/1/枚举值 |
| 金额 / 费率 / 税率 | `decimal(M,D)` | **禁止 `float`/`double`**；单位与精度必须在注释写明（分/元/厘） |
| 日期时间 | `datetime` / `date` | 时区统一；创建/更新时间必填 |
| 名称 / 描述 / 文本 | 合理长度 `varchar(N)` | N 必须有业务依据 |
| 大文本 | `text` / `mediumtext` | 与主表分离，见 2.4 |

**禁止无业务依据的 `varchar(255)` / `varchar(512)`。** 每个 `varchar` 长度必须能说明来源（如手机号 20、身份证 18、车牌 16）。

### 2.2 必备字段

每张业务表必须包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 主键（见第 3 章） | 主键 |
| `create_time` | `datetime` | 创建时间，`DEFAULT CURRENT_TIMESTAMP` |
| `update_time` | `datetime` | 更新时间，`ON UPDATE CURRENT_TIMESTAMP` |

按需可选：`create_by` / `update_by` / `del_flag`（逻辑删除）/ `revision`（乐观锁）/ `remark`。

### 2.3 字符集

统一 `utf8mb4` + `utf8mb4_general_ci`（或项目既定 collation），支持 emoji 与多语言。

### 2.4 大字段分离

`text` / `blob` / 超长 `varchar` 不得与高频查询字段放在同一张热表，避免行溢出与回表放大，必要时拆子表。

## 3. 主键设计规范

### 3.1 核心原理：PolarDB MySQL InnoDB 中「主键 = 聚簇索引」

InnoDB（PolarDB MySQL 存储引擎）中，**表数据按主键顺序物理组织，主键索引的叶子节点直接存放整行数据**——即"主键就是聚簇索引"。这带来两个直接后果：

1. **所有二级索引的叶子节点存的是主键值**（用于回表）。主键越大，每个二级索引就越占空间。
2. **主键的写入顺序决定数据的物理插入位置**。顺序主键顺序追加写；随机主键则在已满的数据页中间插入，触发页分裂。

### 3.2 varchar 主键的三方面影响

以 `varchar(64)`（尤其随机字符串）作主键，相较 `bigint`：

| 影响维度 | 说明 |
|---|---|
| **二级索引空间** | 每个二级索引叶子都要存一份主键值。`varchar(64)` 比 `bigint`（8 字节）大数倍，表上索引越多，膨胀越明显。 |
| **写入性能** | 随机字符串主键导致插入位置随机，B+Tree 频繁**页分裂**、缓存命中下降、写放大。 |
| **页分裂 / 碎片** | 页分裂产生存储碎片，Buffer Pool 有效利用率下降，范围扫描性能变差。 |

### 3.3 双轨策略

- **新表：默认 `bigint`**（聚簇索引友好、二级索引小、顺序写入无页分裂）。

  ```sql
  `id` bigint NOT NULL COMMENT '主键',
  PRIMARY KEY (`id`)
  ```

- **存量：保持 `varchar(64)`**。存量系统 `BusinessEntity.id = varchar(64)`（雪花字符串 ID）**保持不变，禁止自动迁移**。改动需走影响分析 + 迁移 + 回滚 + 风评流程。

- **新表使用 `varchar` 主键**：必须书面说明属于以下之一——外部系统 ID（对接第三方）、跨库全局唯一标识、明确的特殊业务原因。

### 3.4 禁止项

**禁止使用 UUID / 随机字符串作为聚簇主键**（随机写入导致页分裂、二级索引膨胀、写放大）。确需全局唯一，用**有序**方案（雪花/号段），或将随机串放唯一键、主键仍用 `bigint`。

## 4. 索引设计规范

### 4.1 查询驱动（设计前必须分析访问模式）

设计索引前，先分析 SQL 的：`WHERE` / `JOIN` / `ORDER BY` / `GROUP BY` / 分页。**没有查询场景，不设计索引。**

### 4.2 联合索引列顺序

优先级：

```
高选择性等值字段  →  范围字段  →  排序字段  →  覆盖字段
```

### 4.3 规则与案例

每条规则给出正确 / 错误对照。

#### 规则一：最左前缀匹配

联合索引只能从最左列开始连续使用，跳列则右侧列失效。

```sql
-- 索引： KEY idx_user_time (user_id, create_time)
-- ✅ 正确：命中 user_id，再用 create_time 范围+排序，无 filesort
WHERE user_id = ? AND create_time BETWEEN ? AND ? ORDER BY create_time
-- ❌ 错误：跳过最左列 user_id，索引无法使用，退化全表扫描
WHERE create_time BETWEEN ? AND ?
```

#### 规则二：高选择性优先

等值条件里，把区分度高的列放联合索引前列；低选择性（状态、布尔）不建单列索引。

```sql
-- ✅ 正确：user_id 选择性高在前，status 选择性低在后
KEY idx_user_status (user_id, status)
-- ❌ 错误：对低选择性 status 单独建索引，写放大且几乎不被优化器选用
KEY idx_status (status)
```

#### 规则三：覆盖索引（减少回表）

查询所需列都在索引中，即可"索引覆盖"，免回表。

```sql
-- 查询： SELECT user_id, status FROM t WHERE user_id = ?
-- ✅ 正确：覆盖索引，Extra 出现 Using index，无回表
KEY idx_user_status (user_id, status)
-- ❌ 错误：只索引 user_id，status 需回表取行
KEY idx_user (user_id)
```

#### 规则四：索引冗余治理

字段相同或前缀被覆盖的索引属冗余，浪费空间、拖慢写入。

```sql
-- ❌ 错误：idx_user 是 idx_user_time 的前缀，冗余，应删除 idx_user
KEY idx_user (user_id)
KEY idx_user_time (user_id, create_time)
-- ✅ 正确：只保留能覆盖前缀查询的联合索引
KEY idx_user_time (user_id, create_time)
```

### 4.4 索引数量与命名

- 单表索引数量建议 `≤ 5`，高频写表更严格控制（写放大）。
- 命名：普通索引 `idx_<字段简写>`；唯一索引 `uk_<字段简写>`；联合索引名体现关键列。

## 5. SQL 生成硬规则

以下为生成阶段的强制约束，违反视为不合格产出。

### 5.1 禁止 `SELECT *`

必须明确列出字段，避免宽表回表、网络放大、隐式依赖。

### 5.2 禁止函数包裹索引字段

```sql
-- ❌ 禁止（索引失效）
WHERE DATE_FORMAT(statistics_time, '%Y%m%d') = ?
WHERE YEAR(create_time) = ?
WHERE LEFT(car_plate, 3) = ?
-- ✅ 正确：改为范围
WHERE statistics_time >= ? AND statistics_time < ?
```

禁止函数包括但不限于：`DATE_FORMAT`、`YEAR`、`MONTH`、`HOUR`、`LEFT`、`SUBSTRING`、`IFNULL` 等作用在索引列上。

### 5.3 禁止 `LIKE '%xxx%'` 片段模糊

```sql
car_plate = ?              -- ✅ 完整值：走索引，最佳
car_plate LIKE '鲁MA8%'    -- ✅ 前缀：可走索引
car_plate LIKE '%鲁MA8%'   -- ❌ 片段：无法走 BTree 索引
```

片段模糊必须：限制查询范围 + 限制时间窗 + 或改用搜索引擎。

### 5.4 禁止深分页

```sql
-- ❌ 禁止
... LIMIT 100000, 20
```

改用**游标分页**（`WHERE id > ? LIMIT n`）或**延迟关联**（先按索引取主键再 JOIN 回表）。

### 5.5 禁止无 WHERE 的 UPDATE / DELETE

```sql
-- ❌ 禁止
UPDATE table SET ...;
DELETE FROM table;
```

核心表写操作 `WHERE` 必须包含主键/唯一键，并带租户/停车场/商户隔离条件。

### 5.6 批量、事务与 Mapper 约束

- 批量操作分批（建议每批 ≤ 1000，视表宽调整），避免一次性锁表、超长事务。
- 写操作服务层必须 `@Transactional(rollbackFor = Exception.class)`；只读方法不加事务。
- 数据访问必须使用项目统一的 `CommonMapper<T>`，禁止直接使用 MyBatis-Plus 原生 Mapper 基类（详见 `rules/java-mapper-rule.md`）。
- 参数占位使用 `#{}`（预编译，防注入），禁止用 `${}` 拼接用户输入。

## 6. 慢 SQL 与索引失效（PolarDB / MySQL）

### 6.1 常见索引失效场景

| 场景 | 说明 |
|---|---|
| 函数包裹索引列 | 见 5.2 |
| 隐式类型转换 | `varchar` 列传数字、字符集不一致 |
| 前导 `%` 模糊 | `LIKE '%x%'` |
| 违反最左前缀 | 联合索引跳列 |
| `OR` 连接非索引列 | 退化全表扫描 |
| 范围列后再等值 | 范围列之后的联合索引列失效 |
| 排序与索引方向不一致 | `Using filesort` |

### 6.2 EXPLAIN 关注点

核心 SQL 必须给出 `EXPLAIN`，重点看：`type`（避免 `ALL`）、`key`（是否命中预期索引）、`rows`（扫描行数）、`filtered`、`Extra`（避免 `Using filesort`/`Using temporary`/回表过多）。

### 6.3 分析链路（PolarDB / MySQL）

以 PolarDB/MySQL 为准：`slow_log` + `EXPLAIN` + `information_schema`（`statistics`/`tables`）+ 索引选择性分析。**Doris 慢 SQL 分析能力保留、不删除**，但 OLTP 主链路以 PolarDB/MySQL 为准。

## 7. 字段变更与大表 DDL

### 7.1 新增字段"四问"（`add-field` 必须回答）

1. 该字段是否作为查询条件？
2. 是否需要索引？（若是，按第 4 章设计）
3. 是否影响大表？（评估行数与锁表时长）
4. 是否需要在线 DDL？（大表必须）

### 7.2 兼容性

- 新增字段默认可空或给安全默认值，保证新旧代码兼容。
- 默认值不得改变核心状态/金额语义。
- 是否需要历史数据回填，必须说明。

### 7.3 大表 DDL 必备清单

大表结构变更必须提供：表规模评估、锁表时长评估、在线变更方案、前滚脚本、回滚脚本、验证 SQL、执行窗口与责任人。**缺失评估/回滚/验证 SQL 的大表 DDL 视为 P0 风险。**

### 7.4 类型/长度/精度变更

- 类型兼容性（`varchar→bigint`、`int→tinyint` 等）需评估；
- 金额精度、单位变更未验证直接判 P0；
- 迁移策略（双写、回填、灰度）必须明确。

## 8. PolarDB / MySQL 专项规范

> PolarDB MySQL 基于 InnoDB。本章是生成、设计、评审、慢 SQL 治理阶段的 PolarDB 专项权威依据，与第 3 章（主键）、第 4 章（索引）、第 6 章（慢SQL）互为呼应，不重复其规则。

### 8.1 InnoDB 存储结构

#### 聚簇索引
- **主键作为聚簇索引**：InnoDB 中主键即数据的物理组织方式，**数据存储在主键 B+Tree 的叶子节点**。
- 设计影响：
  - **主键长度影响所有二级索引**（二级索引叶子都存主键值，主键越大越占空间）。
  - **主键顺序影响写入性能**（顺序主键顺序追加；随机主键在页中间插入）。
  - **随机 UUID 导致页分裂**（页满后中间插入触发分裂，产生碎片、写放大）。

#### 二级索引
- 二级索引叶子节点保存的是**主键值**（用于回表）。
- 影响：**主键越大，二级索引空间越大**；表上索引越多，膨胀越明显。覆盖索引可免回表（见第 4 章）。

### 8.2 主键设计与性能

- **新表：`bigint`**（自增 或 雪花数值 ID），适合高写入、大数据量场景。
- **存量：`varchar(64)`**，保持兼容，**禁止自动迁移**。
- 详见第 3 章双轨策略；禁止 UUID/随机字符串作聚簇主键。

### 8.3 Buffer Pool

- 包含：数据页缓存 + 索引页缓存。
- 设计建议：**避免大批量扫描污染缓存**（把热点数据挤出 Buffer Pool，命中率下降）。
- 检查：
  - 大 SQL 是否影响热点数据；
  - 是否需要分页；
  - 是否需要归档。

### 8.4 Redo Log

- 作用：保证事务持久性；包含 WAL（Write-Ahead Log）机制与崩溃恢复。
- 风险：**大事务**导致 redo 压力增加、崩溃恢复时间增加。

### 8.5 Undo Log 与 MVCC

- 包含：一致性读、事务隔离、回滚能力。
- 风险：**长事务**导致 Undo 增长、历史版本无法及时清理（purge 阻塞）。
- 规范：**禁止长时间事务操作大批量数据**。

### 8.6 大表治理规范

- **大表定义（参考）**：`500 万+` 行。
- 需要评估：索引数量、查询模式、数据生命周期、归档策略。
- **分区**：适用时间范围数据（如停车流水 `parking_record`）。说明：**不是所有表都需要分区**，仅当按时间大范围查询/归档时考虑。
- **冷热数据分离**：热数据（近期高频访问）与冷数据（历史归档）分层存放。

### 8.7 在线 DDL 规范

新增字段、索引时必须评估：数据量、执行时间、锁影响、回滚方案。

涉及大表时必须考虑在线变更工具：`Online DDL`、`gh-ost`、`pt-online-schema-change`。（呼应第 7.3 节大表 DDL 必备清单）

### 8.8 读写分离

- PolarDB 能力：主节点写、只读节点查询。
- 规范：必须评估**数据一致性要求、延迟容忍度、事务场景**。
- **禁止：强一致业务错误读取只读节点**（主从延迟导致读到旧数据）。

### 8.9 HTAP / 列存索引

- 适用：分析型查询（报表、聚合分析、大范围扫描）。
- 不适合：高频事务查询。
- **必须区分 OLTP 与 OLAP 场景**：OLTP 主链路走行存 + 精准索引；OLAP 大聚合可评估列存索引，避免拖垮事务主链路。

### 8.10 PolarDB 设计自检清单

设计/评审时对照勾选：

- [ ] 主键是否适合聚簇索引（`bigint` 优先、顺序写入）
- [ ] 是否避免随机 UUID 主键
- [ ] 二级索引是否过多（写放大、空间膨胀）
- [ ] 是否存在大表风险（500万+，是否评估分区/归档）
- [ ] 是否评估在线 DDL（大表变更锁影响与回滚）
- [ ] 是否存在长事务风险（Undo 增长、purge 阻塞）
- [ ] 是否合理使用读写分离（一致性/延迟/事务场景）
- [ ] 是否区分 OLTP / OLAP（行存索引 vs 列存）

## 9. 生产案例沉淀

真实生产问题，作为生成与评审的反面教材。

### 案例 1：`parking_record_new` —— 车牌片段模糊导致全表扫描

**问题 SQL**：

```sql
-- ❌ car_plate 上的 BTree 索引完全失效，随数据增长必然慢查询
WHERE car_plate LIKE '%鲁MA8W%'
```

**根因**：前导 `%` 使 BTree 索引无法利用（见 5.3 / 6.1）。

**规范做法**：

```sql
car_plate = ?              -- 完整车牌：走索引
car_plate LIKE '鲁MA8%'    -- 前缀：可走索引
-- 若确需片段检索：限制停车场/时间窗范围，或引入搜索引擎
```

### 案例 2：`parking_lot_statistics` —— 日期函数包裹导致索引失效

**问题 SQL**：

```sql
-- ❌ 对 statistics_time 使用 DATE_FORMAT，索引失效
WHERE DATE_FORMAT(statistics_time, '%Y%m%d') = ?
```

**根因**：函数包裹索引列（见 5.2 / 6.1）。

**规范做法**：

```sql
-- ✅ 改为范围查询，命中 statistics_time 索引
WHERE statistics_time >= ? AND statistics_time < ?
```

禁止的日期/字符串函数包裹：`DATE_FORMAT`、`YEAR`、`MONTH`、`HOUR`、`LEFT`、`SUBSTRING` 等。

## 10. 生成阶段产出物要求

### 10.1 `new-crud` 产出物

除 Entity / Mapper / Service / DubboApi 外，必须补充：

- 表结构 **DDL**（字段类型合规、必备字段齐全）；
- **主键方案**（双轨策略 + 理由）；
- **索引方案**：每个索引须说明**支撑哪个查询**与**为何这样排列列顺序**；
- 关键**查询 SQL**（字段收敛、无禁用写法）；
- **性能风险**说明（查询路径、预期数据量、风险点）。

### 10.2 `new-api` 产出物

接口设计必须包含：查询条件、数据量评估、分页方式（避免深分页）、索引依赖（命中哪个索引，不足则提出新增建议）。**禁止只设计接口而不考虑 SQL。**

### 10.3 `add-field` 产出物

必须回答 7.1 的"四问"，并给出 `ALTER TABLE` 语句、兼容性说明；若涉及大表，给出 7.3 的大表 DDL 清单。

### 10.4 正向设计顺序（禁止先建表后补索引）

```
业务场景 → 访问模式 → SQL → 索引 → 表结构
```

## 11. 生成自检清单（Definition of Done）

生成类 Skill 交付前逐项自检：

- [ ] 遵循业务场景驱动设计顺序（场景→访问模式→SQL→索引→表结构）；
- [ ] 字段类型合规，无无依据的 `varchar(255/512)`，金额用 `decimal`，状态用 `tinyint`；
- [ ] 主键符合双轨策略，新表 `bigint`，`varchar` 主键有理由，未擅改存量结构；
- [ ] 必备字段齐全（`id` / `create_time` / `update_time`）；
- [ ] 索引基于真实查询场景设计，联合索引列顺序正确，无冗余/低选择性单列索引，且每个索引有理由；
- [ ] 无 `SELECT *`；无函数包裹索引列；无 `LIKE '%x%'` 无约束；无深分页；无无 WHERE 的 UPDATE/DELETE；
- [ ] 使用 `#{}` 预编译，使用统一 `CommonMapper<T>`；
- [ ] 写操作有事务，批量分批；
- [ ] 核心 SQL 附索引理由 / 查询路径 / 性能风险说明。
